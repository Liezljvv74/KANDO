# Job Page, Payment Status, Live Checklist and Money View Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One job page per request, a real payment status, a Live checklist that says what is missing, and a provider money view, built as five small pull requests.

**Architecture:** The request becomes the job (no new table; a database-numbered `job_number` on `requests`). One pure server function derives the job state (section, status key, buttons, amounts) from the request, its bookings and the money facts, and replaces the phone's `booking-status.ts` and `pay-state.ts` payment cases. API changes are additive only, so installed builds keep working.

**Tech Stack:** pnpm monorepo, Expo SDK 58 (expo-router, jest-expo), Next.js `app-api/v1` routes wrapped in `appRequest`, Drizzle + hand-written SQL migrations on Neon, vitest (domain, contract, i18n, web integration), Stripe Connect (untouched).

**Spec:** `docs/superpowers/specs/2026-11-06-job-page-design.md` (approved by the owner on 6 November 2026). Where a mockup in `docs/superpowers/specs/assets/2026-11-06-job-page/` and the spec text differ, the text wins (mockups still show 12% and the old "materials" line).

- The owner merges every pull request; never push to `main`; one branch and one pull request per PR below. Before a merge: `/code-review --comment`, fix the findings, remind the owner to submit a GitHub review (Approve).
- No AI co-author and no "Generated with" lines in commits or pull request descriptions (CLAUDE.md overrides any default attribution).

- Additive API only: old fields keep being returned unchanged; new fields are optional for old builds; a new field or screen that needs a new column ships in the app build that uses it.
- Order for every change: migration on production first (additive), then server deploy, then app build only when a screen needs it. PR 1 to 4 are tested by the owner in the phone-sized browser setup (the harness from the UX test, commit `8007415`, kept on the local branch `test/web-agent-harness`, never merged or pushed; cherry-pick it onto a test branch as the README describes); no test build for them. **One test build for the phone, made when PR 5 is ready and before PR 5 is merged** (owner, 6 November 2026; this replaces the earlier "every second PR" rule).
- Money is not touched: `settle.ts`, `webhook.ts`, `ledger.ts`, timers, invoice numbering, thread model and `rls.ts` classes stay as they are (a new column on an existing table needs no new classification).
- Tests per task: only the affected specs and `tsc` (`pnpm typecheck`). Integration specs in `apps/web/tests` hit the dev Neon branch and run one after another (`pnpm --filter web test -- --fileParallelism=false <file>`). Domain, contract and i18n specs: `pnpm --filter <package> test`. Mobile: `pnpm --filter mobile test <file>` (jest, pure logic only, no screen tests). Full suites only at the end of the stage.
- Windows machine: use the editor tools for multi-line edits; never print `.env` values; no secrets in the repo.
- No competitor names; country and currency come from the country record (no new Germany-only assumptions).
- Fixed copy from the spec: Contact support is an email to `info@skillweb.space` with job number and title filled in; Delayed replaces "Payment pending"; provider never sees "Report a problem" on a finished job; header block is two columns by three lines in one font (12px, weight 600, colon after each label): Job #, Customer/Provider, Date (`Sat 14 Nov '26`, German `25.11.'26`), Time, Duration, Location (`10115 Berlin`).

## Review Focus

1. A request with several bookings where the newest is cancelled or declined: the job page and list must show the live booking, not the newest row (task 4.1).
2. An installed build still sends `materialAmount` at "Job finished": accepted and ignored, never a 400 (task 5.3).
3. A provider who loses readiness after a request exists: "Send a quote" refused and greyed with the missing steps; Decline and Open chat still work (task 1.2).
4. A failed refund or payout: both sides see one "Delayed" state; a refund already issued by Stripe counts as done once, not as failed (task 3.3).
5. A person who is customer and provider: each side has its own counter; one job counts once per side; the tab badge is the sum (task 4.3).
